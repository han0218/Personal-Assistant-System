# 个人助手系统手册
**PAS — Personal Assistant System**
版本：v2.0 | 状态：草稿

---

## 一、这是在做什么

PAS 是一个以「状态召回」为核心目标的个人助手系统。

它不是知识管理工具，不是任务管理系统，不是笔记软件。它是一个有记忆的对话伙伴——能随时聊、能在对话中主动浮现相关的历史语境、能在你需要的时候把「当时咋想的」那个状态调回来。

这个系统存在的前提是：你是一个想法活络、跨域联想、不爱刻意整理的人。系统的设计必须顺着这个现实，而不是试图改变它。

---

## 二、核心目标

**首要目标：状态召回**
不是找到一条信息，是找回一个现场——当时在想什么、被什么触发、思路往哪走、说了没说完的那句话。

**次要目标：连续性与交流**
每次对话不从零开始。系统知道你是谁、在关注什么、最近在想什么。书籍作为原材料的一部分进入系统，不只是为了检索，而是让对话能以你读过的东西为基础展开——它是交流的背景，不是查询的数据库。

**衍生目标：被动触发**
你不需要记得有某个旧想法存在。系统在你聊天的过程中，发现当前话题和历史记录的连接，主动把它浮出来。

---

## 三、一个根本区分

**信息 vs 状态**

信息可以脱离你独立存在。「孟子说过什么」写下来就是它自己，谁读都一样。

状态不能独立存在。「我当时咋想的」是一整套东西的组合：当时的关注点、触发源、情绪方向、没说完的半句话。它是一个现场，不是一个条目。

这个区分决定了系统的所有设计选择：
- 为什么原版必须保全——状态只活在未经处理的原始材料里
- 为什么处理层要做薄——处理得越多，失真越多
- 为什么不强求分类——你的想法是流动的，强行分类会切断跨域连接

## 四、理论框架

### 4.1 池子模型

系统的存储核心是一个「池子」——所有原材料按时间顺序堆在一起，不预先分类。

每条记录带以下元数据（写入 Obsidian 属性区）：
- 时间戳（date）
- 一句话标记（title）
- 来源类型（source_type）
- 标签（tags）——聚类的主要手段，从 ROOT.md 的词库中选取
- 状态摘要（summary）——简短描述这条记录的思维状态：卡在哪、哪里没说完、从哪跳到哪没接上。闭合的内容如实写「结论完整」即可

书籍单独存放，不进主池子。原因：书籍是别人的思想，混入会稀释你自己产生的内容。

池子里的原材料来源不同、密度不同，但不做硬性隔离。跨类型的连接是系统最有价值的能力，不应被场景隔离切断。

### 4.2 原版保全原则

任何进入系统的内容，原版必须完整保留，不得被提炼或改写替代。这里的「原版」指**内容原版**，不是文件格式原版——docx 转成 Markdown 存入池子没问题，但绝不允许改写、删减、总结内容本身。

处理层只允许做一件事：在原版之上加标记和索引（属性区字段、标签、摘要）。不改写内容本身。

原因：你和自己想法之间隔的东西越多，状态召回的质量越低。被总结过的想法会失真——读摘要时你以为自己回到了当时，其实只是在读一个关于当时的描述。

「想清楚了」不等于旧记录失效。当你对某个旧疑问得出结论时，新结论作为新记录独立存入池子，旧记录原版保留。新旧记录并排存在，记录的是你从疑问走到结论的完整轨迹。

### 4.3 轻分类原则

系统不强制分类，不建立复杂的目录结构。

参考框架（PARA）可以作为粗粒度的辅助：
- Projects：当前活跃推进的事
- Areas：长期关注的领域
- Resources：书籍、参考资料
- Archives：已沉寂的内容

但这个框架是描述性的，不是强制性的。新内容进来，系统自动判断归属，你不需要手动操作。

### 4.4 标签与链接

标签和链接是系统的两种结构索引，职责不同。

**标签（tags）** 是聚类的主要手段。同一标签下的笔记在 Obsidian 里天然聚合。标签前后兼容——今天给任何一篇笔记加一个标签，它立刻和过去所有同标签笔记归到一起，不受入池先后顺序的影响。CC 入池时自动从 ROOT.md 的标签词库中选取，词库中没有合适的才造新词。

**链接（`[[...]]`）** 是你手动标出的点对点连接——你读到两篇之间有具体而直接的关联时打一条。CC 不自动生成链接。手动链接的价值在于它携带着「你当时注意到了这个关联」的判断，同时 CC 在检索时能顺着链接跳转到相关笔记。只在新文件里加链接，不改旧文件——Obsidian 的反向链接面板会自动补上另一半。

### 4.5 双模调用

**主动检索**：你想起来有某个旧想法，主动问系统，它去池子里找，返回原版。

**被动触发**：你正在聊某个话题，系统发现当前话题和历史记录有连接，主动浮出来——「你之前有个相关的想法/记录，要看吗？」

两种模式同时存在，互相补充。被动触发解决的是「根本想不起来有这个东西存在」的问题，主动检索解决的是「想起来了但找不到」的问题。

### 4.6 被动触发的链条：按需三级

被动触发不靠预先算好的分数公式，靠 CC 作为在场的判断者当场决定。

系统不预先计算排序分数、不使用加权公式。原因：预先算分是「浮现时刻没有判断力在场」时的替代品；PAS 的执行者 CC 本身就是一个会思考的模型，能在浮现时刻直接读材料、做判断。把联想和筛选交给模型当场做，比用一个算术公式近似判断更准、也更灵活。

这意味着系统的「优化旋钮」是协议文件里的自然语言说明，而不是需要调校的数字阈值。浮现不准时，修改协议中对 CC 的指令即可——这是你能读懂、改得动的优化方式。

**三级按需触发：**

- **一级·圈候选**：CC 根据当前话题，通过标签 + 手动链接 + Mem0 语义检索，拉出一批可能相关的笔记。此时 CC 只看 title 和 tags，做最粗的相关性判断。不够就换一批标签再找。
- **二级·读摘要**：对一级筛出的候选，CC 读 summary（状态摘要），判断哪几条值得深入。
- **三级·读全文**：话题确实需要深入时，CC 去调对应笔记的全文来读，做最终判断是否浮现。

三级不是同一次判断里的三步漏斗，而是随对话推进**按需触发**的三次动作。一级随时在跑，二级有苗头才做，三级话题真正深入时才做。

### 4.7 分层上下文

系统对 CC 的上下文采用分层加载策略：

- 根层：一个轻量文件（ROOT.md），描述你是谁、当前活跃的关注点、标签词库
- 项目层：各个活跃方向的具体背景，按需加载
- 原材料层：池子里的具体内容，只在需要深入检索时加载

原因：上下文窗口是有限资源。把所有东西全塞进每次对话，反而会降低召回质量——模型对中间部分的注意力会显著下降。

## 五、架构分工

系统中有四个角色，职责严格分离：

**CC（执行者）** ——唯一的判断者。负责入池处理（转格式、加属性区）、检索时的联想判断、被动触发时的浮现决策。所有需要「理解内容」的事都由 CC 做。通过 Claudian 插件在 Obsidian 内部工作。

**Obsidian（存储）** ——本地 Markdown 库，存原版内容。标签聚合、反向链接、图谱视图都是 Obsidian 提供的——图谱是你看自己思维网络的地方，CC 不使用图谱。

**Mem0（语义检索）** ——存每条笔记的语义向量（通过嵌入模型生成），加上文件路径等元数据。CC 问它「和这段话相关的有什么」，它返回候选的文件路径和摘要。Mem0 不判断、不联想——它是 CC 用来查的工具。从第一天就使用，不分阶段切换。文件有变动（新增或链接更新），CC 自动同步 Mem0。

**标签 + 链接（结构索引）** ——标签聚同类，链接是你手动标的跳转路径。两者共同作为一级候选的来源，和 Mem0 的语义检索互补。

一句话：CC 思考，Obsidian 存储，Mem0 检索，标签和链接提供结构。

## 六、原材料来源

系统接收四类原材料：

| 来源 | 优先级 | 说明 |
|------|--------|------|
| AI 对话记录 | ★ 最高 | 最密集的思维痕迹，优先建立导出流程 |
| 语音/文字随手记录 | 高 | 手机随时捕捉，低摩擦 |
| 已有文档 | 中 | 一次性导入，历史材料 |
| 书籍 | 独立 | 单独存放，不混入主池子。作用是交流背景，而非检索对象 |

**关于历史材料**：过去散落在各平台的对话不追溯。系统从现在开始建，往前追代价过高且意义有限。

## 七、设计原则总结

1. **顺势而为**：系统设计顺着你的真实习惯，不要求你改变行为模式。特别是：系统的复杂度必须压在你能维护的程度——一个你调不动的系统等于没有系统。
2. **原版保全**：状态只活在未经处理的原始材料里，绝不以提炼替代原版。「原版」指内容原版，不是文件格式原版。
3. **轻分类**：分类是辅助，不是负担。标签聚类，系统自动处理，你不手动归档。
4. **本地优先**：数据在你自己的机器上，不依赖第三方服务器，数据主权在你。
5. **薄处理层**：宁可调用时慢一点让 CC 多读原文，也不愿事先把想法嚼碎。
6. **双模并存**：主动检索和被动触发同时运行，互不替代。
7. **判断归模型**：不预先算分、不用加权公式。联想和浮现的判断由 CC 当场做，优化手段是修改协议里的自然语言指令。

## 八、实现路径

**存储层**：Obsidian 本地库，纯 Markdown 文件，数据完全自有。通过 Claudian 插件在 Obsidian 内部与 CC 交互。
**记忆层**：Mem0（GitHub：mem0ai/mem0），从第一天起存储每条笔记的语义索引（title、summary、标签、链接信息），用于快速检索。原版内容始终保留在 Obsidian 池子里——Mem0 发现连接、返回路径，CC 去 Obsidian 调原版。两者分工：Mem0 管检索，Obsidian 管保真。文件有变动 CC 自动同步 Mem0。
**对话导出**：AI Exporter（Chrome 插件），支持 Claude、GPT、Gemini 等主流平台，导出为 Markdown 格式直接入库。
**处理层**：CC 负责读取原始文件，转 Markdown，自动打标签、写状态摘要、建索引，不改写原文内容。具体规则写入系统协议（CLAUDE.md）。
**调用层**：CC + 系统协议分层加载。根层描述你是谁和当前关注点，项目层按需加载，原材料层仅在深度检索时调用。

## 九、分阶段建设

### 阶段一·跑通核心闭环

**目标**：内容能进来、检索能用、系统是活的。

- 装 Obsidian + Claudian + Mem0，建好库结构，放协议文件和 ROOT.md。
- 喂第一批原材料（docx 文章），CC 走完整流程：转 Markdown → 加属性区（title / date / source_type / tags / summary）→ 同步 Mem0 → 原件留档。
- 在真实文件上验证属性区字段够不够用，不合用当场改协议。
- 验证闭环：丢一个话题，CC 能通过「标签+链接圈候选 → 读摘要 → 必要时读全文」找到相关旧笔记，判断准确。

**【阶段门槛 G1】** 10-15 篇真实内容干净入池，属性区经真实验证并固化，你信任 CC 的检索和判断。

### 阶段二·被动触发

**目标**：CC 主动拍你肩膀。

- 在你聊天时，CC 主动感知当前话题与池子的连接，按三级链条判断是否浮现。
- 浮现时给出原版入口，不用转述代替。
- 核心要调的是「什么时候浮、浮多少」——前期从严，宁缺毋滥。调的手段是修改协议中的自然语言指令。

**【阶段门槛 G2】** 浮现时机恰当、频率不烦人、内容有价值。

## 十、当前状态与边界

**已确定的**：
- 系统目标和核心设计原则
- 架构分工（CC 判断、Obsidian 存储、Mem0 检索、标签+链接结构索引）
- 被动触发链条（三级按需、判断归模型、无预算分公式）
- 标签与链接的定位（标签主聚类、链接手动点对点）
- 原材料来源和优先级
- 存储策略（本地优先，Obsidian + Markdown）
- 处理层策略（原版保全 + 加属性区）
- Mem0 从第一天起使用

**待确定的**：
- 摘要的具体写法和质量标准（需在真实文件上验证后固化）
- 标签词库的初始内容（需在 ROOT.md 中建立）
- Mem0 在当前环境中的安装和配置（需实测验证）
- 手机端捕捉入口的具体工具选择

**已知边界**：
- 「你是谁」的部分需要时间沉淀，不是现在能解决的
- 被动触发的质量依赖池子的体量，初期效果有限，需要积累

**搁置项（记录在案，暂不纳入）**：
- 长期问题池（GPT 提出）：系统识别你反复回到的根本问题，显现长期认知主线。有价值，但当前难度已够高。
